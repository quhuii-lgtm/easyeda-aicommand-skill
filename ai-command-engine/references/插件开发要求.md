# Plugin development requirements

Read this page only when developing, modifying, or reviewing plugin commands.

Follow these requirements before the workflow below:

- Implement the feature and make the normal usage flow work before reviewing security and limitations.
- Do not let extra restrictions or development checks block feature implementation.
- A command must do what it promises and the plugin must check the result itself.
- Do not make development notes, test steps, or acceptance procedures prerequisites for ordinary use.
- Do not add useless restrictions for developer convenience, historical issues, or host differences.
- Adapt the plugin to host differences; do not use extra restrictions as a substitute for fixing them.
- Perform checks inside the plugin when the plugin can do them; do not shift them to the user.
- Keep only checks needed to prevent modifying the wrong project, using the wrong connection, duplicate writes, or clear runtime errors.
- For every new restriction, state the specific error it prevents and first consider handling it inside the plugin.
- When the result is knowable, explicitly return success or failure; do not always return “needs verification.”
- When the result truly cannot be confirmed, explain why and stop operations that depend on it. Do not automatically retry a write with an unknown result.
- Before delivery, check that the normal usage flow completes; compilation alone is not sufficient.

- When modifying an object through an asynchronous handle, await `done()` and then fetch the object independently for verification. A batch `get` may return fewer items when some IDs do not match; match by primitive ID instead of array position, and do not verify through a stale modified handle.
- The IFrame API used by the DFM menu is marked beta by the official documentation. Treat that as development compatibility context; do not disable a verified menu or add user-confirmation steps solely for that reason.

## Plugin-internal source-record handling

For plugin implementation only. Do not write document source directly for ordinary drawing.

- Document source is a line-oriented JSON change log (`JSON(header)||JSON(data)`). For the same `(type,id)`, `ticket` determines the newest record; empty `data` is a deletion tombstone. It is not a snapshot.
- Safe writes are append-only: do not edit old lines; append changes at the end.
- Set `ticket` monotonically from `max+1`.
- Modify a primitive by shallow-copying its original `data` and overriding only the required keys.
- When moving a component, update both coordinate field pairs together: `x/y/angle` and `positionX/positionY/rotation`.
- Delete by appending a tombstone; do not physically remove a line.
- Back up the complete source before writing. Read it back and compare each value (tolerance 0.001). Restore the full backup on failure; save only after all checks pass.
- Prefix generated primitives with `spg_` and use document layer `layerId=13` so they can be cleaned up. The pipeline is wrapped by `pcb.groupBySchematicRegions` and `pcb.sourceRollback` in `src/pcb/sourcelog.ts`.
